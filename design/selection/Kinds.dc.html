In the gutter these are ordinary numbered markers. In the document, a structural or visual anchor gets a 2px outline on the element rather than a text highlight — the Custom Highlight API paints ranges, so a block anchor is an outline, not a fill.
A DECISION THIS FORCES — anchorStateFor()
Today every resolution below layer 1 reports moved: if (!resolution) return "orphaned";
if (resolution.layer === 1) return documentChanged ? "moved" : "ok";
return "moved"; Element anchors resolve at layer 3. That was fine while they were a rare fallback — but make them a primary way to comment and every table and figure comment is permanently amber, on a document nobody has touched. With the wash cards, a table-heavy review turns the whole column amber and the signal stops meaning anything.
RECOMMENDED — no new state, no new field Report ok when a layer‑3 match came from a stable id on an unchanged document. An id match on untouched bytes is exact — calling it “moved” is the resolver being wrong in the cautious direction, which still trains people to ignore the badge. Keep moved for a match found only by css path. create.ts already warns that a positional path “still matches something, so the comment lands on an unrelated paragraph” — that genuinely deserves the badge. Needs one change: resolveElement() reports whether it matched by id or by path. isStableId() already exists to judge the id.
THE ONE THAT FAILS SILENTLY A region is geometry. Redraw the chart and x/y/w/h still resolve — onto different content, reporting success. That is precisely the failure the anchor work exists to prevent, and it is the one kind here that can produce it. Proposal: store a fingerprint of the element's rendered content alongside the region — img src plus dimensions, or a hash of the SVG source. Mismatch on resolve means orphaned, with the comment kept and its quote intact. This is a new field on RegionRef and needs your call before I draw it into the anchor spec.
